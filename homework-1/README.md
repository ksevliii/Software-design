
# Дз-1: SOLID · DI-контейнер · юнит-тесты

Консольное приложение учёта парка «ВышКат» с соблюдением принципов SOLID и применением DI-контейнера. Обеспечивает приём техники с техосмотром, формирование отчётов по числу единиц и суммарной энергии, фильтрацию техники для новичков и вывод полного инвентарного списка.

## Принципы SOLID и DI
1. **SRP** (Single Responsibility Principle)

- `Fleet` отвечает только за управление парком (добавление, отчёты)
- `ServiceCenter` отвечает исключительно за логику техосмотра (валидация и правила)
- `cmd/cli-app` разделён по зонам ответственности: main.go (сборка), demo.go и interactive-mode.go (сценарии), input.go (парсинг ввода), print.go (форматирование вывода)

2. **OCP** (Open/Closed Principle)

Добавление нового вида транспорта (например, гироскутера), реализующего только какие-либо из существующих интерфейсов, требует только создания новой структуры в `internal/inventory/` и реализации нужных интерфейсов. Код `Fleet`, `ServiceCenter` и точка сборки в `main.go` не требуют изменений (ниже про то, что будет, если потребуется новый интерфейс)

3. **LSP** (Liskov Substitution Principle)
Все типы техники взаимозаменяемы через интерфейсы. Метод `Fleet.AddItem` работает с любым объектом, реализующим `Inventarizable`, не завися от конкретной реализации и не нарушая ожидаемого поведения

4. **ISP** (Interface Segregation Principle)

Вместо одного толстого интерфейса в `internal/inventory/interfaces.go` введено 5 узких:
- `Inventarizable`: базовый инвентарный учёт (номер и тип)
- `EnergyConsuming`: наличие суточного расхода энергии
- `SimplicityEvaluated`: наличие оценки простоты использования
- `Chargeable`: наличие аккумулятора и уровня заряда
- `Braked`: наличие тормозной системы

Так, простые объекты (например, `Helmet` или `VehicleStand`) реализуют только `Inventarizable`. 

В модуле техосмотра (`service/tech-inspection.go`) опциональные возможности проверяются через type assertion:
```go
if chargeable, ok := item.(inventory.Chargeable); ok
```

5. **DIP** (Dependency Inversion Principle) и **DI-контейнер**

Модуль `Fleet` зависит от абстракции `service.TechInspector`, а не от конкретной реализации `ServiceCenter`.
Для управления зависимостями реализован строго типизированный DI-контейнер (`internal/di.Container`).

В рамках данного проекта требуется всего одна зависимость. Я считаю, что подключение тяжёлых фреймворков было бы явным overengineering, а данная реализация DI-контейнера выступает некоторым *Composition root*

### Подмена зависимости в тестах
В юнит-тестах `internal/service/service_test.go` демонстрируется изоляция логики парка от логики техосмотра через инициализацию тестового DI-контейнера и инспектора:
- Создаётся заглушка `FakeInspector`, реализующая интерфейс `TechInspector`
- Инициализируется тестовый контейнер: 
```go
container := di.NewContainer(&FakeInspector{AcceptAll: true})
```
- Зависимость извлекается из контейнера `testContainer.TechInspector` и передаётся в методы `Fleet`, при этом `Fleet` ничего не знает о существовании контейнера и получает зависимость через параметры методов

## Ответы на обязательные вопросы

1. **Какой принцип SOLID применён наиболее явно и где?**

ISP. В `internal/inventory/interfaces.go` введено 5 узких интерфейсов. Это позволяет объектам вроде `Helmet` реализовывать только `Inventarizable`, не имея бессмысленных для них методов `ChargePercent()` или `BrakesWorking()`

2. **Какой принцип сознательно ограничен / «почти нарушен» и почему это приемлемо?**

OCP формально ограничен в `ServiceCenter.IsAccept()` из-за использования *type assertion*. При добавлении принципиально нового интерфейса (например, `Flyable`) потребуется добавить новый if в этот метод. Однако это компромисс: в Go невозможна перегрузка методов, а *type assertion* позволяет избежать создания методов-заглушек и используется даже в реализации стандартной библиотеки. Поэтому в учебном проекте выбор пал на простоту и особенности ЯП

3. **Что сломается при добавлении нового вида транспорта, сотрудника или склада запчастей?**
- *Новый транспорт*: не сломается ничего. Добавляется новая структура, реализующая нужные интерфейсы, кроме случая, когда нужен новый интерфейс (об этом в п.2)
- *Сотрудники*: по ТЗ они не ставятся на баланс, поэтому не реализуют `Inventarizable` и не попадают в `Fleet`. При необходимости для них создаётся отдельный сервис и интерфейс
- *Склад запчастей*: не сломается ничего. Запчасти могут реализовать `Inventarizable` и добавляться в парк, либо быть вынесены в отдельный модуль (например, `Warehouse`)

4. **Какой тест фиксирует решение техосмотра и правило «для новичков»; как подменяется зависимость?**

- Техосмотр: `TestServiceCenter_IsAccept` - table-driven тесты
- Для новичков: `TestFleet_BeginnerFriendly_FiltersByScore`, `TestFleet_BeginnerFriendly_EmptyFleet`

**Подмена зависимости**: В тестах создаётся FakeInspector, который передаётся в `di.NewContainer()`. Затем зависимость извлекается как `container.TechInspector` и передаётся в `Fleet`. Также в тестах DI-контейнера создается `FakeInspector`, содержащий в себе поле id, для проверки изолируемости разных контейнеров

5. **Что сделал ИИ, а что изменили вы?**

ИИ использовался как консультант по особенностям Go, его идиоматике и принципам, а также быстрого поиска статей для изучения дополнительного материала. С помощью ИИ генерировались некоторые тестовые кейсы и редактировались формулировки в README

**Самостоятельно выполнены**: архитектурное решение о разделении интерфейсов, расширение модели техосмотра (добавление проверок заряда и тормозов), разбиение cli-app по SRP, написание подмены через DI в тестах и отказ от внешних фреймворков во избежание overengineering

## Особенности и обоснование спорных моментов реализации

1. Отклонение от ТЗ

Так как в ТЗ не было явно сказано о критериях прохождения техосмотра, были добавлены параметры заряда и тормозов. Поэтому необходимы следующие условия для добавления в парк:
- номер не короче 3 символов
- валидное значение метрики простоты (при наличии)
- для устройств с аккумулятором: достаточный и валидный процент заряда (от 70% до 100% включительно)
- для колесных устройств: исправные тормоза

2. Минималистичный DI-контейнер

Контейнер реализован как строго типизированная структура. 
Возможные альтернативы:
- `map[string]any`. Будут ошибки и паники при опечатках в строковых ключах, а также риск потери типобезопасности
- Дженерики. Удобны для большого количества зависимостей, однако для одной это усложнение кода без реальной пользы
- Готовые фреймворки. Для проекта с одной зависимостью подключение тяжёлых фреймворков было бы избыточным

Текущая реализация гарантирует проверку типов на этапе компиляции и легко масштабируется добавлением новых полей в структуру

3. Отсутствие тестов на UI, тривиальные конструкторы и геттеры

Юнит-тесты предназначены для тестирования поведенческой логики, а не тривиальных методов: тесты вида `if s.Type() != "Шлем"` не ловят реальные ошибки

**Фактическое покрытие:**
- `internal/service`: 95% (поведенческие + граничные случаи через table-driven tests)
- `internal/di`: 100% (все методы контейнера)
- `internal/inventory`: соответствие интерфейсам через *type assertion*
- `cmd/cli-app`: 0% (UI-слой не тестируется юнит-тестами)

Значения получены через
```bash
go test -cover ./...
```
