# Дз-2: DDD · архитектура · паттерны GoF

Консольное приложение "ПОС" - Преподавательская Оценка Студентов. Обеспечивает учёт студентов и критериев оценивания, выставление и исправление оценок, расчёт итогового балла по весам и экспорт результатов. Данные сохраняются в JSON и восстанавливаются после перезапуска.

## Структура проекта

```text
cmd/pos/                    точка входа, параметры запуска
internal/
  domain/                   студенты, критерии, оценки, курс, расчёт итога
  application/              пользовательские сценарии и порты
  adapters/
    console/                меню, чтение ввода и вывод результатов
    jsonstore/              JSON-хранилище, преобразование данных
    csvexport/              экспорт итогов в CSV
  di/                       сборка зависимостей через samber/do/v2
```

## Запуск

Перейти в директорию проекта:

```bash
cd homework-2
```

Требуется `Go` не ниже версии в `go.mod`, для команд `make` необходим `Make`

Установить зависимости:

```bash
go mod download
```

Запуск приложения в строгом режиме:

```bash
make run
```

Запуск с нулями за пропущенные оценки:

```bash
make run-zero
```

Выбор папки хранения:

```bash
make run-strict DATA_DIR=./data
```

Альтернатива без Make:

```bash
go run ./cmd/pos -data ./data -mode strict
go run ./cmd/pos -data ./data -mode missing_as_zero
```

Параметры запуска:

- `-data` - папка хранения курсов, по умолчанию `data`;
- `-mode` - режим расчёта: `strict` или `missing_as_zero`, по умолчанию `strict`.

Сборка и проверки:

```bash
make build
make test
make vet
```

Автоматическая демонстрация:

```bash
make demo
```

## Основные сценарии

- Создание и просмотр курсов.
- Добавление и просмотр студентов.
- Подготовка и просмотр рубрикатора.
- Выставление, исправление, отмена и просмотр оценок.
- Расчёт итога по студенту.
- Экспорт итогов курса в CSV.

Если отменить оценку по одному из критериев:
- в строгом режиме итог не рассчитывается из-за пропуска
- в режиме `missing_as_zero` все пустые оценки учтутся как нули

### Пример работы приложения

1. Создать курс `demo`.
2. Добавить студента `s1` с именем "Ксюша".
3. Подготовить и подтвердить рубрикатор:
   - `hw` - "Домашняя работа", максимум `20`, вес `40`;
   - `exam` - "Экзамен", максимум `10`, вес `60`.
4. Выставить студенту `16` по `hw` и `7` по `exam`.
5. Рассчитать итог, ожидается `7.40`.
6. Экспортировать итоги в `results.csv`.
7. Перезапустить приложение с той же папкой хранения и проверить сохранённые оценки (все добавленное должно остаться в json и воспроизвестись при перезапуске).

## Доменная модель и DDD

### Ubiquitous Language

В коде используются те же понятия, что и в предметной области:

- `Student` - студент;
- `Criterion` - критерий оценивания;
- `Grade` - оценка;
- `Rubricator` - рубрикатор, набор критериев;
- `Course` - курс;
- `FinalScoreService` - расчёт итогового балла.

Итог получается из оценок и рубрикатора, не хранится как независимо редактируемое число.

### Entity

`Student`, `Criterion` и `Course` имеют собственные идентификаторы.

Например, студенты с одинаковыми именами, но разными ID - разные сущности. Имя студента не используется для определения его идентичности. Для идентификаторов введены отдельные типы `StudentID`, `CriterionID` и `CourseID`, что помогает не перепутать аргументы при вызове методов.

### Value object

`Grade` выбран как Value Object:

- не имеет отдельного идентификатора;
- содержит ID студента, ID критерия и балл;
- при исправлении заменяется новым значением.

В текущей модели нет истории изменений и отдельного жизненного цикла факта оценивания. 

### Агрегат

Корень агрегата - `Course`. Он управляет студентами курса, рубрикатором и выставленными оценками. Изменения выполняются через методы курса. Внутренние слайсы, мапы и т.п. закрыты, методы чтения списков возвращают отдельные слайсы. Курс проверяет согласованность между объектами: студент должен существовать, критерий должен входить в рубрикатор, повторная оценка для той же пары студент-критерий запрещена.

### Инварианты

Локальные ограничения проверяются при создании объектов:
- ID и имя студента непустые;
- ID и название критерия непустые;
- максимум и вес критерия положительные.

Правила выставления оценок охраняются доменом:
- балл находится в диапазоне `[0, max_score]`;
- студент записан на курс;
- критерий существует в рубрикаторе;
- для пары студент-критерий существует не более одной оценки;
- исправление и отмена применяются только к существующей оценке.

Проверки выполняются до изменения состояния. Например, попытка исправить `7` на `12` при максимуме `10` возвращает ошибку и сохраняет прежнюю семёрку.

### Repository

Порт `application.CourseRepository` описывает операции:

- `Load` - загрузить курс;
- `Save` - сохранить курс;
- `ListIDs` - получить список курсов.

Конкретная реализация находится в `adapters/jsonstore`. Домен не знает о JSON, путях и файловой системе.

### Domain Service

`domain.FinalScoreService` получает актуальные данные курса и передаёт их выбранной стратегии расчёта.

Сервис не читает консоль, не сохраняет файлы и не формирует CSV. Его ответственность - получение итогового результата из доменных данных.


## Архитектура Ports and Adapters

Слои:
- **Domain** - сущности, значения, агрегат, инварианты и расчёт.
- **Application** - пользовательские сценарии и интерфейсы внешних операций.
- **Adapters** - консоль, JSON-хранилище и CSV-экспорт.
- **DI** - выбор конкретных реализаций и сборка приложения.

Направление зависимостей:
```text
console -> application, domain
jsonstore -> application, domain
csvexport -> application

cmd/pos -> di, jsonstore, csvexport
di -> application, domain, console, samber/do
```

`domain` не импортирует консоль, файловые адаптеры или DI-библиотеку. `application` не импортирует конкретные реализации хранения и экспорта.

Консоль - входящий адаптер: запускает сценарии. 
JSON-хранилище и CSV-экспорт - исходящие адаптеры: выполняют внешние операции по запросу приложения.

Замена JSON-хранилища потребует новой реализации `CourseRepository` и изменения регистрации в DI, но не изменения правил выставления оценок.

## Паттерны GoF

**Builder - порождающий**

В `internal/domain/rubricator.go` реализован `RubricatorBuilder`, который отделяет поэтапную подготовку критериев от использования готового рубрикатора.

- `Add` проверяет корректность критерия и отсутствие повторяющегося ID.
- `Build` запрещает пустой набор и создаёт рубрикатор с отдельной копией карты критериев.

В консоли пользователь добавляет критерии, затем подтверждает или отменяет подготовку. Только после подтверждения готовый рубрикатор передаётся курсу и сохраняется. При отмене состояние курса не меняется.

При повторной подготовке Builder заполняется существующими критериями, а новые дополняют набор. Последующее изменение Builder не влияет на ранее построенный рубрикатор.

Паттерн позволяет работать с незавершённой заготовкой, не изменяя действующие правила оценивания до подтверждения.

**Facade - структурный**

В `internal/application/service.go` и `export.go` реализован `application.Service`, предоставляющий консоли единый вход в пользовательские сценарии.

Например, для выставления оценки консоль вызывает:

```go
service.AssignGrade(courseID, studentID, criterionID, score)
```

Сервис загружает курс через репозиторий, вызывает доменную операцию и сохраняет результат. Аналогично он организует расчёт и экспорт итогов.

Паттерн скрывает координацию компонентов за методами сценариев: консоль отвечает за ввод и вывод, а не за работу с хранилищем, расчётом и сохранением данных. Доменные правила при этом остаются внутри модели.

**Strategy - поведенческий**

В `internal/domain/score_calculation.go` определён интерфейс `FinalScoreStrategy` с методом `Calculate` и две его реализации:

- `StrictStrategy` - запрещает расчёт при наличии пропущенных оценок;
- `MissingAsZeroStrategy` - рассчитывает итог, учитывая пропуски как нули.

`FinalScoreService` получает стратегию через конструктор и вызывает её через общий интерфейс. Конкретная реализация выбирается в DI по параметру запуска `-mode`.

Паттерн позволяет менять политику обработки пропусков без изменения сценариев приложения и консоли. Взвешенная формула одинакова для обеих стратегий, поэтому её реализация вынесена в общую закрытую функцию.

## DI-контейнер

Используется `github.com/samber/do/v2`.

Конкретные адаптеры JSON-хранилища и CSV-экспорта создаются в точках входа `cmd/pos/main.go` и `cmd/demo/main.go`. В сборку они передаются через интерфейсы `CourseRepository` и `FinalScoreExporter`.

В `internal/di`:
- переданные адаптеры регистрируются через `do.ProvideValue`;
- провайдеры стратегий и сервисов регистрируются через `do.Provide`;
- `do.Invoke` разрешает зависимости и создаёт сервис приложения.

`BuildService` собирает общий сервис пользовательских сценариев. `BuildApp` использует его и дополнительно создаёт консоль.

## Расчёт итогового балла

Используется шкала от `0` до `10`:

```text
итог = 10 * sum(вес * балл / максимум) / sum(вес)
```

Каждая оценка нормируется относительно максимума своего критерия.

Пример:

```text
Домашняя работа: 16 из 20, вес 40
Экзамен: 7 из 10, вес 60

Итог = 10 * (40 * 16/20 + 60 * 7/10) / 100 = 7.4
```

Веса относительные: `40 и 60` дают тот же результат, что `2 и 3`. Требования суммы весов, равной `100`, нет.
Баллы целочисленные, округление итога до двух знаков выполняется только при выводе и экспорте

### Пропущенные оценки

Выставленный ноль и отсутствие оценки различаются через `HasGrade`.

- В режиме `strict` для расчёта нужны оценки по всем критериям.
- В режиме `missing_as_zero` пропуски учитываются как нули, но реальные нулевые оценки в журнал не добавляются.

## Хранение и экспорт

**JSON-хранилище**

Каждому курсу соответствует файл:

```text
data/<course-id>.json
```

Сохраняются студенты, критерии, оценки и блокировка рубрикатора.

При загрузке проверяются:
- корректность JSON и типов полей;
- отсутствие неизвестных полей;
- отсутствие дополнительных JSON-значений после объекта;
- доменные ограничения при восстановлении;
- совпадение ID курса в файле с запрошенным.

Сохранение выполняется через временный файл в той же папке. Сначала проверяются запись и закрытие, затем файл переименовывается в основной.

**CSV-экспорт**

CSV содержит столбцы:

```text
course_id,student_id,name,mode,score,status
```

- `calculated` - итог рассчитан;
- `incomplete` - строгий режим не позволил получить итог из-за пропусков.

При `incomplete` поле балла пустое. В режиме нулей за пропуски статус `calculated` означает наличие результата, а не наличие всех оценок. Для записи используется `encoding/csv`.

## Тесты

Тесты домена проверяют:
- `student_test.go` - создание студента, пустые значения и нормализацию строк;
- `criterion_test.go` - создание критерия, положительные максимум и вес;
- `rubricator_test.go` - дубликаты, пустой набор, поиск, сортировку и независимость коллекций;
- `course_test.go` - диапазон баллов, существование студента и критерия, повторное выставление, исправление, отмену и блокировку;
- `score_calculation_test.go` - формулу итога, относительные веса, отличие нуля от пропуска и обе стратегии.

Запуск:

```bash
make test
make vet
```

Вместе:

```bash
make check
```

При EOF приложение завершает работу, а не продолжает бесконечно печатать меню. Ошибка чтения Scanner также прекращает работу.

Тесты сосредоточены на инвариантах и расчёте итога в `internal/domain`, как рекомендует ТЗ.

Покрытие пакета `domain` равно `73.4%`, значение получено командой:

```bash
go test -cover ./internal/domain
```

## Особенности и обоснование реализации

### **Блокировка рубрикатора**: после первой оценки запрещена замена рубрикатора, даже если затем все оценки отменили.

Выбранное ограничение модели, что после начала оценивания правила фиксируются. Оно позволяет не реализовывать миграцию существующих оценок при изменении максимумов или удалении критериев. Блокировка сохраняется в JSON и восстанавливается при загрузке.

### **Проверки на нескольких уровнях**: консоль проверяет формат ввода и заранее обнаруживает некоторые ошибки, чтобы не запрашивать лишние поля.

Домен повторно защищает свои правила независимо от консоли, что необходимо, чтобы прямой вызов метода или загрузка данных не позволяли обойти ограничения.

### **Ограниченный набор операций**

Редактирование и удаление студентов и критериев не реализованы. По ТЗ эти операции реализуются по необходимости, основное внимание уделено оценкам. Дата, комментарий, история изменений и апелляции также не входят в текущую версию.

### **Файловое хранение**

Приложение рассчитано на последовательную работу одного процесса. Одновременное изменение курса несколькими экземплярами не поддерживается. CSV-экспорт перезаписывает существующий отчёт напрямую, при ошибке записи он может остаться неполным. Родительская папка отчёта должна существовать.
